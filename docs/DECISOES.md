# Caligo — Registro de Decisões

Versão 1.1

## Como funciona

Toda decisão tem ID, status e consequência. `FIXO` só muda por RFC em `docs/rfcs/`. `PROVISÓRIO` muda com nota no histórico. O escopo define o produto; este documento preserva o raciocínio para que a decisão não seja reaberta por memória seletiva.

| ID | Status | Decisão | Motivo | Consequência |
|---|---|---|---|---|
| D-001 | FIXO | Nenhum sistema entra se não aparecer numa cena jogável. | O protótipo provou sistemas isolados e não produziu um jogo. | Toda release termina em algo visível e jogável. |
| D-002 | FIXO | Duas colunas: cidade densa e natureza estilizada. | É o campo onde a Caligo pode ser referência real. | Nenhum sistema entra sem servir a uma das duas colunas. |
| D-003 | FIXO | Núcleo em C++20; gameplay em C# sobre .NET 10 LTS. | C++ sustenta o desempenho; C# sustenta a iteração. | A fronteira é uma ABI C estável, com custo de hospedagem e marshaling. |
| D-004 | FIXO | Windows 10/11 x64 e Direct3D 11 FL11_0 na v1. | Um alvo só permite qualidade de produção. | A RHI nasce preparada para DX12, mas a v1 não entrega DX12. |
| D-005 | FIXO | Um executável com editor e runtime; a cena é a fonte única de verdade. | Elimina divergência entre autoria e jogo. | Play usa snapshot e descarta o estado ao parar. |
| D-006 | FIXO | Sem placeholder, stub ou código morto. | Código provisório vira fundação falsa. | O CI barra marcadores e o revisor barra implementação incompleta. |
| D-007 | FIXO | TDD; compilação e teste da engine apenas no CI. | O ambiente local não é confiável para Windows. | Todo commit da engine é validado no GitHub Actions antes de ser considerado pronto. O jogo do usuário não depende desse CI. |
| D-008 | FIXO | Todo sistema visual tem teste de imagem determinístico. | "Parece certo" não é critério. | WARP, 300 frames para sistemas temporais e imagem dourada versionada. |
| D-009 | FIXO | Sem comentários no código. | Nome e estrutura devem explicar; comentário apodrece. | O CI rejeita comentários em C++, CMake e Python. |
| D-010 | FIXO | Decisão fixa só muda por RFC escrito. | Impede reabertura por impulso no meio de uma release. | O RFC contém problema, opções, custo, impacto e decisão. |
| D-011 | FIXO | O nome é Caligo, sem sufixo. | Uma marca, um produto, sem versão no nome. | A empresa continua Kizuri Studio; a engine é Caligo. |
| D-012 | FIXO | Sem rede, VR, mobile, console ou macOS na v1. | Cada plataforma multiplica o custo de produção. | Nenhuma abstração é criada para plataformas fora do alvo. |
| D-013 | FIXO | Sem visual scripting. | O gameplay é C# e o editor não carrega duas linguagens. | Ferramentas de autoria geram C# ou dados, nunca grafos. |
| D-014 | FIXO | Sem engine genérica, marketplace ou plugins de terceiros. | A Caligo serve aos jogos do estúdio, não a um ecossistema. | Toda API é desenhada para o produto, não para adoção externa. |
| D-015 | FIXO | Sem ray tracing obrigatório e sem fotorrealismo. | O alvo é estilizado e o piso é FL11_0. | Técnicas de imagem priorizam estabilidade e custo, não física exata. |
| D-016 | FIXO | Stack da seção 5 do escopo, sem vcpkg. | Dependências fixas e reproduzíveis. | FetchContent com tag fixa; atualização de dependência é mudança deliberada. |
| D-017 | FIXO | Asset fonte em formato aberto; runtime lê apenas cozido. | Fonte diffável e pacote rápido e estável. | Nenhum parser de formato aberto roda no jogo. |
| D-018 | FIXO | Meta de 1080p60 numa GTX 1060 6 GB. | Define o orçamento real de cada sistema. | Regressão acima de 10% no orçamento quebra a release. |
| D-019 | PROVISÓRIO | Piso de hardware: FL11_0, 2 GB de VRAM, 8 GB de RAM. | Garante alcance sem sacrificar o alvo. | Pendente de confirmação da GPU de teste do estúdio. |
| D-020 | FIXO | UI de jogo separada do editor: markup, estilo em folha e binding por view-model. | UI de jogo é conteúdo; ImGui é ferramenta. | Dois sistemas, dois orçamentos, nenhuma dependência cruzada. |
| D-021 | FIXO | Limite rígido de linhas por arquivo, verificado no CI. | Arquivo monolítico é o defeito mais caro de corrigir. | Exceção só por allowlist com motivo; entrada obsoleta quebra o CI. |
| D-022 | FIXO | Limite de 600 linhas em `.cpp` e 400 em `.h`. | A R2 confirmou o valor com código real: nenhum arquivo chegou perto do limite. | Funções até 80 linhas; tipos até 20 métodos públicos. |
| D-023 | FIXO | Código proprietário; repositório público apenas para o CI gratuito. | O limite de minutos do CI privado impede o fluxo de validação. | Todo direito é reservado; visibilidade pública não concede licença. |
| D-024 | FIXO | JSON de cena e de ferramentas usa nlohmann/json 3.12.0. | Biblioteca header-only, sem dependência de toolchain extra, com tag fixa. | Parsing e gravação ficam restritos a cena e ferramentas; o runtime lê apenas o contêiner cozido. |
| D-025 | FIXO | Coordenadas canhotas, com +X à direita, +Y para cima e +Z para frente. | Direct3D 11 e DirectXMath já usam essa convenção; evita conversão por frame. | O espaço de visão tem Z positivo à frente; importadores convertem ativos de fontes destras. |
| D-026 | FIXO | Play-in-editor usa snapshot, tick fixo de 60 Hz, pausa e avanço de quadro. | A autoria precisa ficar isolada da simulação. | Parar restaura o snapshot; edição, salvamento e gizmo ficam bloqueados durante a execução. |
| D-027 | FIXO | Hospedagem de script framework-dependent com runtime .NET privado no artefato, contexto coletável e shadow copy. | O editor não pode depender do runtime da máquina nem bloquear os assemblies durante a recarga. | O artefato leva `runtime/dotnet`, `runtime/host` e `runtime/gameplay`; cada execução recria o contexto gerenciado. |
| D-028 | FIXO | Projeto é um descritor de conteúdo, não um diretório implícito: nome, raiz de conteúdo, cena inicial e assembly de gameplay próprios. | Dois jogos do estúdio não cabem na mesma árvore de conteúdo com um único assembly fixo ao lado do executável. | O hub do editor cria, abre e alterna projetos na R3; o runtime resolve conteúdo e gameplay pelo descritor. Até a R3, o editor usa um projeto implícito. |
| D-029 | FIXO | O corpo ativo é tecnologia própria, com nome Tônus: motores que perseguem alvos de animação, equilíbrio, reflexo, cambaleio e levantar, compostos por comportamentos afináveis por dados. | O corpo que reage como gente é o que separa um mundo vivo de um mundo de bonecos, e isso exige nome, contrato e autoria como conteúdo. | Nada de middleware licenciado e nada copiado; é módulo próprio acima de animação e física, porque a pose tem um dono só; nível de comportamento por distância. Primeiro estágio junto do personagem da R4; o documento de sistema nasce na release que o implementar. |
| D-030 | FIXO | Câmera é componente de cena, com lente e seleção da câmera ativa; o comportamento de câmera é script C#. | A lente é dado de cena, versionável e editável no inspetor; o comportamento é gameplay e itera em C#. | A R4 entrega o componente e o play passa a renderizar pela câmera ativa; o viewport mantém a câmera livre do editor. |
| D-031 | FIXO | O editor é organizado por ferramentas: escolher uma ferramenta reorganiza layout, painéis e o que o viewport aceita; o viewport só faz interação 3D; play é global, não uma ferramenta. | Controles soltos na barra do viewport e uma tela única tornam o editor amador e não escalam para terreno, ambiente, animação e UI. | Cada ferramenta tem layout e painel próprios; a hora do céu sai do viewport; F5 a F8 funcionam em qualquer ferramenta. |
| D-032 | FIXO | Identidade visual de 13 px de base, espaçamento compacto e ícones em três camadas: Lucide 1.68.0 na UI, Fluent UI System Icons nos assets e um conjunto Caligo próprio para os tipos da engine; sem trocar ImGui e ImGuizmo. | A densidade e os ícones separam uma ferramenta profissional de um formulário; ícone de ação e ícone de tipo são trabalhos visuais distintos e um conjunto só não cobre os dois bem; trocar a stack custaria mais do que melhorar o tema. | Métricas e tokens fixos; o código semântico do ícone é o contrato e o glifo é implementação substituível; a stack D-016 continua. Ref.: RFC-001. |
| D-033 | FIXO | Céu, hora, clima, exposição e sombras pertencem à ferramenta Ambiente e ao ambiente da cena, não à barra do viewport. | Esses dados são da cena, versionáveis e compartilhados pelo play e pelo build; um slider no viewport não tem dono. | A cena ganha ambiente estruturado; pré-visualização do editor é temporária e não é gravada; o viewport fica só com interação 3D. |
| D-034 | FIXO | Configurações em quatro seções — projeto, cena, editor/usuário e render; os dados vivem em `.cproject`, `.cscene` e `%APPDATA%/Caligo/editor.json`, com precedência engine → projeto → cena → pré-visualização. | Sem escopo, configuração de usuário vaza para o pacote ou o build depende da máquina. | O build lê projeto e cena; configuração de usuário e preview nunca entram no pacote; a tela de Configurações é uma ferramenta. |
| D-035 | FIXO | Componentes são tipos registrados com nome estável `caligo.*`; `caligo.transform` é obrigatório e único; o inspetor tem Adicionar componente; tipo desconhecido falha a carga com diagnóstico e o cook preserva os dados. | O inspetor não pode conhecer cada componente no código e a cena precisa de contrato estável e diagnóstico honesto. | Registro declara nome, categoria, ícone, multiplicidade e fábrica; adicionar e remover são undo; componente desconhecido nunca é descartado em silêncio. |
| D-036 | FIXO | A identidade de um asset importado é um GUID de 128 bits no sidecar `.cmeta`; a cena guarda o GUID no próprio arquivo; mover ou renomear não muda o GUID; GUID nunca é reutilizado; sub-assets são mapeados por caminho estável na fonte. | Referência por caminho quebra com mover e renomear; o runtime precisa de identidade estável. | `.cmeta` versionado ao lado da fonte importada; GUID ausente é recriado com aviso; referência quebrada falha com diagnóstico. |
| D-037 | FIXO | Importar é uma etapa determinística do cook: fonte + configurações + versão do importador produzem bytes idênticos; erro acontece no cook, nunca no runtime. | O jogo não pode pagar parsing nem descobrir conteúdo inválido em execução. | Cache por chave; parser de formato aberto só no cook; o runtime lê `.casset` e manifesto. |
| D-038 | FIXO | glTF 2.0 é o único formato de modelo da v1; FBX, Draco e BasisU ficam fora; a lista de extensões aceitas é fechada. | Formato aberto e superfície fechada reduzem risco, licença e manutenção. | FBX falha com orientação de exportar glTF; extensão obrigatória desconhecida falha; opcional desconhecida avisa. |
| D-039 | FIXO | LOD, tangentes, UV de lightmap, colisão e compressão são automáticos por padrão, com override por asset; geometria inválida falha o cook. | O pipeline precisa ser produtivo sem exigir decisão manual em cada asset, mas sem esconder erro. | Padrões por tipo; `.cmeta` sobrescreve; diagnóstico explica toda decisão automática. |
| D-040 | FIXO | O contêiner cozido cobre cena, malha, textura, áudio, material, modelo, esqueleto, animação, colisão, navmesh, HLOD, terreno, UI, fonte, metadados de script e manifesto; a malha v2 tem UV1, skinning, submalhas e morph targets. | O contêiner da R1 só cobria cena, malha, textura, áudio e UI; o alvo exige dados que o runtime não tem. | Versão de esquema por tipo; malha v2; o cook grava sempre a versão atual; o runtime recusa versão maior desconhecida. |
| D-041 | FIXO | Scripting é por projeto: a engine embute Roslyn e compila o assembly do jogo ao salvar (editor) ou no build (CLI), com diagnóstico, último assembly válido, PDB, anexo por IDE externo e F5/F8; o jogo não exige SDK, MSBuild, NuGet ou CI. | O fluxo profissional não pode depender de toolchain instalada nem de compilação manual; a iteração precisa ser de segundos. | Processo auxiliar `Caligo.Compiler` no runtime privado; referências fixas; build falha com erro; play continua no último assembly válido durante a sessão. |
| D-042 | FIXO | Produzir um jogo é local e autossuficiente; não depende de CI, rede ou GitHub; o CI existe apenas para desenvolver e validar a engine. | O desenvolvedor precisa construir e entregar sem serviço externo; CI por jogo multiplica custo e falha. | Cook, compilação, stage e zip rodam na máquina; o CI pode gerar o jogo de exemplo como prova da engine. |
| D-043 | FIXO | Build local por CLI: cook, compilar scripts, montar stage e zip; um executável com modos editor e jogo; só conteúdo cozido; manifesto; build ID por conteúdo; sem instalador, updater, loja ou assinatura na v1. | Um caminho único e reproduzível é mais valioso que várias opções de empacotamento. | `caligo.exe build` e o botão do editor chamam a mesma implementação; pasta e zip; runtime privado e CRT estática. |
| D-044 | FIXO | Terreno por tiles: heightfield com escultura, camadas de material, importação/exportação de heightmap, LOD por clipmap, colisão e vegetação; pincel determinístico e undo por traço. | Um pincel de cores com resolução fixa não é terreno de produção nem se compara à RAGE. | `.cterrain` como asset; ferramenta Mundo com painel próprio; tile de 512 m e 512 amostras no padrão. |
| D-045 | FIXO | O renderer evolui em estágios, sem reescrita monolítica: malha e material PBR, CSM, velocity TAA, cel e contorno, clusters e instancing, SSR e névoa, pós. | A R2 já tem uma base correta; reescrever tudo atrasaria a produção e arriscaria a estabilidade. | Cada release mantém a engine utilizável; a ordem pode mudar por release, o princípio não. |
| D-046 | FIXO | A v1 é Windows x64; port é projeto pós-v1, com backend gráfico, camada de plataforma, empacotamento, runtime .NET e imagens douradas próprias. | Um alvo só permite qualidade de produção; port não é flag nem promessa de marketing. | CMake recusa outro sistema; o pacote é `windows-x64`; nenhuma abstração é criada para plataforma fora do alvo. |

## Histórico

- **1.1** — reescreve a D-032 por RFC-001: ícones em três camadas (Lucide na UI, Fluent UI System Icons nos assets e conjunto Caligo próprio para os tipos da engine), no lugar de "Lucide para tudo".
- **1.0** — registra D-031 a D-046: editor por ferramentas, identidade de 13 px e Lucide, Ambiente, configurações em quatro seções, registro de componentes, `.cmeta`, importação determinística, glTF, automação de importação, contêiner ampliado, scripting por projeto com Roslyn embutido, build local, terreno profissional, renderer em estágios e Windows x64 como único alvo; esclarece que o CI da D-007 é da engine e que o hub de projetos entra na R3.
- **0.9** — registra a D-030: câmera como componente de cena, comportamento em script C#.
- **0.8** — confirma o limite de arquivo da D-022 como fixo, depois da R2.
- **0.7** — corrige a fronteira do Tônus: módulo próprio acima de animação e física, porque a pose tem um dono só.
- **0.6** — registra a D-029: corpo ativo como tecnologia própria, com nome Tônus.
- **0.5** — registra a D-028: projeto como descritor de conteúdo com raiz, cena inicial e assembly próprios.
- **0.4** — registra a D-026 e a D-027: snapshot de play e hospedagem de script com runtime privado.
- **0.3** — registra a D-025: coordenadas canhotas com Z positivo à frente.
- **0.2** — registra a D-024 e a biblioteca JSON da stack.
- **0.1** — registro inicial das decisões D-001 a D-023.
